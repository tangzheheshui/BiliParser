## 1. 改造范围与原则

客户端已有完整可运行的程序，含：标题栏、操作区、左上角设置、左下角状态栏、激活入口与激活窗口 UI。

**本档只讲三件改逻辑的事：**
1. 对接服务器激活接口（替换现有鉴权请求实现）；
2. 激活成功后持久化保存服务器下发的凭证；
3. 每次启动改为本地校验凭证，不再联网校验。

**保持现状不动的部分：**
- 操作区及所有业务功能；
- 设置页两个必填配置（B 站字幕提取字符串、API Key）及现有配置方法；
- 左下角状态栏（含红绿字显示两个配置就绪状态 + 激活状态）；
- 激活窗口 UI、"未激活点关键按钮提示去激活"交互。

> 开发者：不要重做任何已有 UI，只在原有结构里替换/补全鉴权逻辑。

---

## 2. 客户端与服务器仅剩的交互

通知功能已移除，客户端与服务器现在只有**一种**交互：**激活**（仅在需要激活时调用一次，一次性的）。

```
启动 → 读本地凭证 → 通过：直接用（不联网）
                → 失败：弹激活窗口 → 调激活接口 → 成功存凭证 → 用
```

日常运行**完全离线**，服务器宕机对已激活用户零影响。

---

## 3. 激活接口对接（改造点 1）

### 3.1 调用时机

仅在本地凭证不存在或本地校验失败（文件损坏、被篡改、换机器）时，由用户在激活窗口输入激活码、点击"激活"按钮触发。

### 3.2 请求

```
POST /api/v1/license/activate
请求体：{ "mac": "<本机 MAC 规范化前原值>", "sn": "<用户输入的激活码原值>" }
超时：10 秒
```

> 客户端无需做 MAC 大小写/分隔符规范化——服务器侧已规范化，客户端只需把本机 MAC 原值上送即可。激活码也无需客户端预格式化，服务器统一大写化。

### 3.3 返回码处理（沿用现有 UI，只改逻辑分支）

| code | 含义 | 客户端处理 |
|---|---|---|
| `0` | 激活成功（含重装后同机恢复） | 保存凭证（见第 4 节）→ 关闭激活窗口 → 进入主程序；状态栏激活状态置"已激活" |
| `1` | 未激活（未输码就发起了请求） | 保持激活窗口（正常客户端不会触发，兜底分支） |
| `2` | 无效激活码 | 输入框标红："激活码无效，请检查输入" |
| `3` | 设备不匹配 | 提示："该激活码已被其他设备使用" |
| `4` | 参数错误（MAC 为空） | 提示异常（正常客户端不会触发，属程序 bug 兜底） |
| `500` | 服务器内部错误 | 提示"网络异常，请稍后再试" |
| 网络超时/不可达 | —— | 提示"网络异常，请稍后再试"；已激活用户不受影响（本地凭证仍有效） |

### 3.4 输入预处理

- 激活码输入框：自动去除首尾空格与内部 `-` 分隔符、自动转大写，支持直接粘贴（沿用现有实现即可，若已做则不动）；
- 激活按钮：请求期间置灰防重复提交（沿用现有实现，若已做则不动）。

## 4. 本地凭证存储（改造点 2）

### 4.1 凭证内容

激活成功（`code=0`）后，从响应 `data` 中取出并持久化保存：

| 字段 | 来源 | 用途 |
|---|---|---|
| `sn` | 服务器响应 | 用于显示与将来再次激活 |
| `mac` | 服务器响应（规范化后值） | 本地校验时与当前本机 MAC 比对 |
| `activated_at` | 服务器响应 | 签名输入的一部分 |
| `token` | 服务器响应 | 服务器签名，本地验签 |

### 4.2 存储位置

沿用客户端现有的本地存储机制（注册表/配置文件均可，按现有工程实现习惯走）。

> 若现有工程无统一本地存储，推荐：Windows 注册表 `HKEY_CURRENT_USER\Software\<产品名>\License`，或用户目录下配置文件。
> 卸载时不主动清除，便于用户重装软件直接复用凭证。

### 4.3 凭证完整性

凭证四字段作为一个整体存取，任一字段缺失即视为凭证无效，触发激活窗口。

---

## 5. 启动本地校验（改造点 3）

### 5.1 流程

每次启动主程序入口处，执行本地校验：

1. 读取本地凭证，四字段齐全则继续，否则 → 走激活流程；
2. 用**内置的签名密钥**（与服务器 `LICENSE_SIGN_KEY` 完全一致）按相同算法重算 `HMAC-SHA256(secret, sn + "|" + mac + "|" + activated_at)`，与凭证中的 `token` 比对；
3. 取当前本机 MAC，规范化后与凭证中的 `mac` 比对；
4. 步骤 2、3 全过 → 鉴权通过，直接进主程序，**不联网**；
5. 任一步骤失败 → 走激活流程（不要直接判死，覆盖重装/换机场景）。

### 5.2 关键规则

| 编号 | 规则 |
|---|---|
| CR-01 | 已激活客户端日常启动**全程不联网**，拔网线也能正常使用 |
| CR-02 | 凭证校验失败时回退到激活窗口，不弹死错（覆盖重装系统、本地文件损坏） |
| CR-03 | 本机 MAC 取法必须与激活时一致（取第一块有效物理网卡，多网卡环境固定策略） |
| CR-04 | 内置签名密钥需与服务器 `LICENSE_SIGN_KEY` 同步管理，两边必须完全一致 |

### 5.3 安全边界（写给开发者）

> 本方案目标是**防"一码多机传播"与随手篡改凭证**，不是防专业逆向。签名密钥随客户端分发，理论上可被提取；MAC 也可被有心人伪造。对一款小工具此防护等级足够，**不要**追加加壳/反调试等复杂度。

## 6. 与状态栏、设置页的衔接

仅说明逻辑接口，UI 已有不动：

- **状态栏激活状态字段**：本地校验通过 → 显示"已激活"；本地校验失败/无凭证 → 显示"未激活"。由鉴权模块在校验完成后回写状态。
- **未激活点关键按钮**：现有"点击关键功能按钮提示去激活"逻辑保留，触发条件改为"本地校验未通过"（而非"在线校验未通过"）。
- **设置页两个必填配置**与鉴权完全独立，鉴权改造不影响其配置与校验逻辑。
- 状态栏两个配置的红绿字显示逻辑不动。
- **官网链接**：客户端底部（原通知位置）放一个固定的官网链接字符串，写死在客户端里即可，点击在系统默认浏览器打开。**不需要联网拉取**，不需要服务器配合，链接地址由官网侧维护即可。改造时移除原通知拉取相关的全部代码与调用。

## 7. 验收标准

| # | 场景 | 预期 |
|---|---|---|
| 1 | 首次启动（无凭证） | 出现激活窗口（沿用现有 UI） |
| 2 | 输入有效码激活成功 | 关闭激活窗口，进入主程序，状态栏显示"已激活"，本地生成凭证 |
| 3 | 激活后断网重启 | 正常进入主程序（全程无联网） |
| 4 | 手动篡改凭证文件中的 MAC | 校验失败 → 回到激活窗口 |
| 5 | 把凭证拷贝到另一台机器 | 校验失败（MAC 不匹配）→ 激活窗口 |
| 6 | 重装系统后用原码原机重新激活 | 服务器返回 code=0，重新拿到凭证，进入主程序 |
| 7 | 输入不存在的码 | 提示"激活码无效" |
| 8 | 输入已被别的机器激活的码 | 提示"该激活码已被其他设备使用" |
| 9 | 服务器宕机时启动已激活客户端 | 一切正常，无任何报错 |
| 10 | 未激活时点关键功能按钮 | 提示"去激活"（沿用现有逻辑） |
| 11 | 设置页两个必填配置就绪 | 状态栏两字段显示绿字（沿用现有逻辑，鉴权改造不影响） |
| 12 | 改造完成后，通知相关代码/调用全部移除 | 客户端不再发起任何通知请求 |
| 13 | 底部官网链接 | 显示为固定字符串，点击在默认浏览器打开官网，全程不联网请求 |
