# 需求：Web 工作台

> 状态：已实现（2026-08）。本文档记录原始需求、迭代需求、设计决策与边界。

## 原始需求（v1）

来自用户（2026-08-18）：

> 我想要个 html 页面，里面是个工作区，可以分成三份区间，一个是操作按钮的一些，
> 一个是视频链接 和 视频预览区域，然后右侧是文本分析区域（有原始文本 总结文本
> 等其他显示方式）

## 功能范围

三栏工作区布局：

| 区域 | 内容 |
|---|---|
| 左：操作区 | 文本生成按钮（拉取字幕 / 标准总结 / 详尽总结 / 元数据+热评 / 降级 AI 总结）、配置状态卡（SESSDATA、GLM Key、模型、端点） |
| 中：链接与预览 | 链接输入框 + 解析、B 站嵌入播放器、视频信息卡（标题 / UP / 时长 / 数据 / 标签 / 简介 / 分 P 切换） |
| 右：文本分析区 | 四个页签：原始字幕（带时间戳高亮）、标准总结、详尽总结、元数据+热评；工具栏支持复制 / 导出 .md / 清空 |

行为细节：

- 解析视频后按钮才可用；任一操作进行中全局禁用（避免并发打爆 B 站接口）
- 视频/字幕按 BV 缓存在服务进程内，切页签、重复总结不重复拉取
- 无字幕或无 SESSDATA 时，字幕与总结操作给出带提示的报错，引导用「元数据+热评」降级模式
- 降级 AI 总结的结果显示在「元数据+热评」页签，并带「推断性结果」警示条

## 设计决策

1. **零新依赖**：后端用 Python 标准库 `http.server`（ThreadingHTTPServer），
   前端单文件原生 HTML/CSS/JS，无构建步骤。理由：本项目定位自用小工具，
   依赖越少越好修（README「已知边界」的同一哲学）。
2. **复用 CLI 模块**：`web.py` 只做 HTTP 编排，业务全部走既有的
   `bilibili` / `subtitle` / `meta` / `summarizer` / `config` 模块，与 CLI 行为一致。
3. **内置 Markdown 渲染**：前端带约 40 行的极简渲染器（标题/列表/加粗/行内代码/
   链接/引用），覆盖总结模板用到的语法；不引入 CDN 依赖，离线可用。
4. **嵌入播放器**：`player.bilibili.com` iframe 预览；iframe 内未登录，清晰度受限，
  仅作预览用。

## API 一览

| 路由 | 说明 |
|---|---|
| `GET /` | 工作台页面 |
| `GET /api/status` | 配置状态（不触网） |
| `POST /api/parse` | `{url, page?}` → 视频信息 + 标签 |
| `POST /api/subtitle` | `{url, page?}` → 字幕全文（按 cid 缓存） |
| `POST /api/summarize` | `{url, page?, mode: standard\|detailed\|meta}` → Markdown |
| `POST /api/meta` | `{url}` → 元数据+热评上下文（不花 LLM） |

业务异常（BiliError / ConfigError / SummarizeError）统一转 HTTP 4xx +
`{error, hint}`；未预期异常转 5xx。

## 迭代需求（v2，同日）

来自用户：

> 左侧工作区可以丰富一些，比如文本生成类型除了这几个复杂度之外还可以自定义，
> 用户可以自定义一些提示词，然后格式可以保存；然后想支持多个网址的，可以切换，
> 然后右侧 2 个工作区随之切换

### 自定义模板

- 左栏「自定义模板」区：新建（名称 + 提示词）/ 编辑 / 删除，点模板名即对当前视频生成
- 模板持久化在 `~/.biliparser/prompts.json`，跨会话可用
- 生成结果作为动态页签出现在右栏（★ 前缀 + 模板名），与内置页签并列，可复制/导出/清空
- 后端：`summarizer.summarize_custom()`（复用超长视频 map-reduce），
  `POST /api/prompts` 新建/更新、`GET /api/prompts` 列表、`DELETE /api/prompts/<id>` 删除

### 多视频工作区

- 中栏顶部视频页签：连续解析多个视频，各自一个工作区，随时切换/关闭
- 每个工作区独立保存：播放器、视频信息、四个内置页签内容、自定义模板结果、当前激活页签
- 切换时中栏（预览）与右栏（文本分析）随之整体切换，互不干扰
- 服务端按 BV 缓存视频信息与字幕（多 P 按 cid），前端切换零额外请求

来自用户：

> 1. 点击生成后的时间可以跳转到视频对应位置播放吗；
> 2. 网址输入框每次只能输入一个吗？我输入第二个的时候就覆盖第一个了，换个更好的展现形式和输入形式；

## 迭代需求（v5）：字幕完整性

用户反馈：「我的视频 20 几分钟，现在就能总结 2 分多钟的」。

排查发现三个叠加的坑，统一修在 `bilibili.fetch_full_subtitle()`：

1. **残缺 CC 被优先选中**：实例 BV1G7gZ6VEEE，UP 后补的 CC 字幕只有
   1 行 / 27 秒（9%），语言优先级规则（CC > AI）无脑选它 → 修复后
   下载所有候选、按覆盖时长挑最完整的，同分才按语言优先级
2. **AI 字幕 CDN 版本彩票**：同视频每次新签名 URL 随机落到不同节点，
   实测返回 1% ~ 79% 的不同版本（疑似 B 站渐进生成/同步中，视频
   BV1HZgV6TEGm 23:22 实测）→ best-of-8 轮重试（每轮重新取列表拿新
   URL），跨轮保留最佳，覆盖率 ≥80% 提前收手
3. **URL 的 `?p=N` 被忽略**：多 P 视频默认解析 P1 → CLI 与 Web 均支持
   从链接取分 P 参数

覆盖率 <60% 时 CLI 打印警告、Web 在字幕页签顶部显示黄色警示条。
附注：BV1G7gZ6VEEE 的视频内容当天被 UP 替换过（沃尔玛探店 → 核能主题），
同 BV 不同时间的字幕内容会不同。

### v5b：字幕「串台」检测

用户实测同一视频多次总结内容各异（LoL 解说 / 麦当劳复刻 / 韩综——而视频本身
是西游记解读，发布于当天）。结论：**新发布视频的 AI 字幕有串台期**，CDN 各节点
会返回完全不属于本视频的字幕文件，且覆盖率指标失效（错文件也能 100%）。

对策（三层）：

1. `fetch_full_subtitle` 用「各次下载的首行指纹」做一致性检测（同一视频的
   合法版本渐进生成只增不改，首行应一致），不一致 → `consistent=False`
2. CLI 打印警告、Web 字幕页签显示红色警示条
3. 总结 prompt 加护栏：字幕与标题/简介明显无关时拒绝总结，说明字幕实际内容

附注：当天早上 BV1G7gZ6VEEE 的「沃尔玛」总结亦是串台产物（视频实为乡村日常），
已删除误导文件。新发布视频请等 B 站字幕生成稳定后再总结。

## 已知边界 / 后续

- 时间戳跳转采用整帧重载播放器，会有一次短暂刷新（跨域限制下的折中）
- 多视频工作区为会话级状态，刷新页面即清空（后续可考虑 localStorage 持久化）
- 服务仅监听 127.0.0.1，无鉴权（本机自用，不要暴露到公网）
